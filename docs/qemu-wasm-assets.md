# QEMU-WASM Runtime Asset Acquisition Guide

This document describes the runtime asset requirements, expected directory layout, compilation procedure, and artifact name mapping for running QEMU-WASM AArch64 in reachOS.

reachOS **does not vendor precompiled binaries** or fake runtime files. All WebAssembly and guest OS assets must be built from traceable, licensed upstream sources and placed into the designated static asset directory.

---

## 1. Upstream Artifact Name Mapping

To avoid deployment failures, understand how upstream filenames map to reachOS deployment paths:

| Artifact Role | Upstream Build Output | Upstream `examples/raspi3ap` Browser Name | reachOS Manifest Name | Notes / Loader Constraints |
| :--- | :--- | :--- | :--- | :--- |
| **JS Runtime** | `build/qemu-system-aarch64.js` | `qemu-system-aarch64.js` | `qemu-system-aarch64.js` | Core Emscripten loader. Looks for `<prefix>.wasm` and `<prefix>.worker.js` matching its prefix. |
| **Wasm Binary** | `build/qemu-system-aarch64.wasm` | `qemu-system-aarch64.wasm` | `qemu-system-aarch64.wasm` | Core emulator module. Must match `qemu-system-aarch64.js` naming. |
| **Pthread Worker** | `build/qemu-system-aarch64.worker.js` | `qemu-system-aarch64.worker.js` | `qemu-system-aarch64.worker.js` | Worker entry point for `PROXY_TO_PTHREAD=1`. |
| **Guest FS Loader**| Generated by `file_packager.py` | `load.js` | `load.js` | Generated script that loads the guest package into Emscripten virtual filesystem. |
| **Guest Data Bundle**| Generated by `file_packager.py` | `qemu-system-aarch64.data` | `qemu-system-aarch64.data` *(canonical)*<br>`load.data` *(alternative)* | **Critical**: `load.js` hardcodes the data package name passed to `file_packager.py`. If built with `qemu-system-aarch64.data`, the file on disk must be `qemu-system-aarch64.data`. If built with `load.data`, the file on disk must be `load.data`. |

---

## 2. Expected Directory & File Layout

Place all runtime and guest assets in the static assets directory:

```
public/qemu/
├── qemu-system-aarch64.js          # Required: Emscripten runtime loader
├── qemu-system-aarch64.wasm        # Required: Compiled QEMU AArch64 Wasm binary
├── qemu-system-aarch64.worker.js   # Required: Emscripten pthread Web Worker script
├── load.js                         # Required: Preloaded filesystem loader script
└── qemu-system-aarch64.data        # Required: Packaged kernel, DTB, and initramfs bundle
                                    # (Accepted alternative: load.data)
```

> **Note:** During the Angular build process, files placed in `public/` are automatically copied to the browser distribution root (`dist/app/browser/qemu/`). The server endpoint checks both locations.

## 3. Building Upstream Artifacts

Upstream project: [https://github.com/ktock/qemu-wasm](https://github.com/ktock/qemu-wasm)

### Prerequisites
* Linux host (x86_64 or aarch64) with Docker installed.
* Git.

### Step-by-Step Build Procedure

1. **Clone the upstream repository:**
   ```bash
   git clone https://github.com/ktock/qemu-wasm.git
   cd qemu-wasm
   ```

2. **Launch the Docker build container (Emscripten SDK):**
   ```bash
   # Build the container environment with Emscripten and pre-compiled libraries (GLib, Pixman, zlib)
   docker build -t build-qemu-wasm .
   docker run -it --rm -v $(pwd):/workspace -w /workspace build-qemu-wasm bash
   ```

3. **Configure and build `qemu-system-aarch64`:**
   Inside the build container:
   ```bash
   mkdir -p build && cd build
   emconfigure ../configure \
     --target-list=aarch64-softmmu \
     --static \
     --disable-tools \
     --disable-guest-agent \
     --extra-cflags="-O3 -matomics -mbulk-memory -sASYNCIFY=1 -pthread -sPROXY_TO_PTHREAD=1 -sALLOW_TABLE_GROWTH=1 -sWASM_BIGINT=1 -sTOTAL_MEMORY=2048MB"
   emmake make -j$(nproc)
   ```
   This generates in `build/`:
   * `qemu-system-aarch64.js`
   * `qemu-system-aarch64.wasm`
   * `qemu-system-aarch64.worker.js`

4. **Prepare and package guest OS images (Raspberry Pi 3 A+ reference example):**
   Upstream provides a pre-packaged build recipe in `examples/raspi3ap/image/`:
   ```bash
   cd ../examples/raspi3ap/image
   docker build -t build-raspi3ap-image .
   docker run --rm -v $(pwd):/out build-raspi3ap-image
   ```
   Package the kernel, DTB, and BusyBox initramfs into Emscripten virtual filesystem files using `file_packager.py`.
   Following upstream's documented command line:
   ```bash
   python3 $EMSDK/upstream/emscripten/tools/file_packager.py \
     qemu-system-aarch64.data \
     --preload zImage@/zImage bcm2837-rpi-3-a-plus.dtb@/bcm2837-rpi-3-a-plus.dtb rootfs.cpio@/rootfs.cpio \
     --js-output=load.js
   ```
   This generates:
   * `load.js`
   * `qemu-system-aarch64.data`

   *(If you alternatively ran `file_packager.py load.data ...`, it produces `load.data`. Both names are recognized by the reachOS asset detector, but the filename on disk must match what `load.js` expects.)*

---

## 4. Deployment into reachOS

Copy the generated outputs into the reachOS workspace:

```bash
mkdir -p public/qemu
cp build/qemu-system-aarch64.js public/qemu/
cp build/qemu-system-aarch64.wasm public/qemu/
cp build/qemu-system-aarch64.worker.js public/qemu/
cp load.js public/qemu/
cp qemu-system-aarch64.data public/qemu/
# (or cp load.data public/qemu/ if packaged as load.data)
```

---

## 5. Verifying Asset Presence via Status API

After copying the files, query the server endpoint:

```bash
curl -s http://localhost:3000/api/qemu/status
```

Expected status states:
* **`assets_missing`**: No required files found in `public/qemu/`.
* **`assets_incomplete`**: Some files present, but missing others (lists `missingRequired`).
* **`assets_present_unverified`**: All required files are present on disk. The response will accurately report `detectedFilename` for each asset (e.g. `qemu-system-aarch64.data` vs `load.data`). Note that `bootVerified` remains `false` until client-side execution is implemented and verified.
