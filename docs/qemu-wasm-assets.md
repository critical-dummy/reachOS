# QEMU-WASM Runtime Asset Acquisition Guide

This document describes the runtime asset requirements, exact upstream compilation commands, artifact names, and verification procedure for running QEMU-WASM AArch64 in reachOS.

reachOS **does not vendor precompiled binaries** or fake runtime files. All WebAssembly and guest OS assets must be built from traceable, licensed upstream sources and placed into the designated static asset directory.

---

## 2. Expected Directory & File Layout

Place all runtime and guest assets in the static assets directory:

```
public/qemu/
├── qemu-system-aarch64.js          # Required: Emscripten runtime loader (or out.js)
├── qemu-system-aarch64.wasm        # Required: Compiled QEMU AArch64 Wasm binary
├── qemu-system-aarch64.worker.js   # Required: Emscripten pthread Web Worker script
├── load.js                         # Required: Preloaded filesystem loader script
└── qemu-system-aarch64.data        # Required: Packaged guest kernel, DTB, and rootfs bundle
```

> **Note:** During the Angular build process, files placed in `public/` are automatically copied to the browser distribution root (`dist/app/browser/qemu/`). The server endpoint checks both locations.

## 3. Verified Reproducible Build Procedure

To build genuine upstream QEMU-WASM artifacts from source, use a Linux build host with Docker (BuildKit enabled) and Git.

### Step 1: Clone Upstream Repository
```bash
git clone https://github.com/ktock/qemu-wasm.git
cd qemu-wasm
git checkout 0ef7b4e2814b231705d8371dd7997f5b72e70baf
```

### Step 2: Build and Launch the Emscripten Build Container
```bash
docker build -t buildqemu - < Dockerfile
docker run --rm -d --name build-qemu-wasm -v $(pwd):/qemu/:ro buildqemu
```

### Step 3: Configure and Compile `qemu-system-aarch64`
Execute the exact upstream configuration and build command inside the container:
```bash
EXTRA_CFLAGS="-O3 -g -Wno-error=unused-command-line-argument -matomics -mbulk-memory -DNDEBUG -DG_DISABLE_ASSERT -D_GNU_SOURCE -sASYNCIFY=1 -pthread -sPROXY_TO_PTHREAD=1 -sFORCE_FILESYSTEM -sALLOW_TABLE_GROWTH -sTOTAL_MEMORY=2300MB -sWASM_BIGINT -sMALLOC=mimalloc --js-library=/build/node_modules/xterm-pty/emscripten-pty.js -sEXPORT_ES6=1 -sASYNCIFY_IMPORTS=ffi_call_js"

docker exec -it build-qemu-wasm emconfigure /qemu/configure --static --target-list=aarch64-softmmu --cpu=wasm32 --cross-prefix= \
  --without-default-features --enable-system --with-coroutine=fiber --enable-virtfs \
  --extra-cflags="$EXTRA_CFLAGS" --extra-cxxflags="$EXTRA_CFLAGS" --extra-ldflags="-sEXPORTED_RUNTIME_METHODS=getTempRet0,setTempRet0,addFunction,removeFunction,TTY,FS"

docker exec -it build-qemu-wasm emmake make -j $(nproc) qemu-system-aarch64
```
This generates in `/build/` inside the container:
* `/build/qemu-system-aarch64` *(executable JavaScript file without .js extension)*
* `/build/qemu-system-aarch64.wasm`
* `/build/qemu-system-aarch64.worker.js`

### Step 4: Build raspi3ap Guest OS Images via Docker BuildKit
Execute the upstream multi-stage BuildKit image build:
```bash
mkdir -p /tmp/pack/
DOCKER_BUILDKIT=1 docker build --output=type=local,dest=/tmp/pack/ ./examples/raspi3ap/image/
```
This generates directly into `/tmp/pack/`:
* `kernel8.img` (64-bit Linux kernel Image compiled from `raspberrypi/linux` tag `1.20230405`)
* `bcm2710-rpi-3-b-plus.dtb` (Raspberry Pi 3 Model B/A+ Device Tree Blob)
* `rootfs.bin` (ext4 filesystem image containing static BusyBox 1.36.1 and `/etc/init.d/rcS`)

### Step 5: Package Guest Files using Emscripten `file_packager.py`
Copy the pack directory into the build container and invoke `file_packager.py`:
```bash
docker cp /tmp/pack build-qemu-wasm:/
docker exec -it build-qemu-wasm /bin/sh -c "/emsdk/upstream/emscripten/tools/file_packager.py qemu-system-aarch64.data --preload /pack > load.js"
```
This produces:
* `/build/load.js` (with embedded `PACKAGE_NAME = 'qemu-system-aarch64.data'`)
* `/build/qemu-system-aarch64.data`

## 4. Deployment into reachOS

From the host machine, copy the generated artifacts into `public/qemu/`:

```bash
mkdir -p public/qemu

# Copy the runtime JavaScript loader:
# As out.js (matching upstream README):
docker cp build-qemu-wasm:/build/qemu-system-aarch64 public/qemu/out.js
# Or as qemu-system-aarch64.js:
# docker cp build-qemu-wasm:/build/qemu-system-aarch64 public/qemu/qemu-system-aarch64.js

# Copy Wasm binary and worker script (keep canonical names):
docker cp build-qemu-wasm:/build/qemu-system-aarch64.wasm public/qemu/
docker cp build-qemu-wasm:/build/qemu-system-aarch64.worker.js public/qemu/

# Copy guest virtual filesystem files:
docker cp build-qemu-wasm:/build/load.js public/qemu/
docker cp build-qemu-wasm:/build/qemu-system-aarch64.data public/qemu/
```

## 5. Verifying Asset Presence via Status API

After copying the files, query the server endpoint:

```bash
curl -s http://localhost:3000/api/qemu/status
```

Expected status states:
* **`assets_missing`**: No required files found in `public/qemu/`.
* **`assets_incomplete`**: Some required files are missing, OR `load.js` exists but its required `PACKAGE_NAME` is unparseable or does not match the `.data` file on disk (`loaderCompatible: false`).
* **`assets_present_unverified`**: All required files are physically present on disk AND `load.js` is verified to match `qemu-system-aarch64.data` (`loaderCompatible: true`).

### Limitations of Static Asset Checks
The `/api/qemu/status` endpoint performs filesystem verification and loader package compatibility checks. It **does not execute** the WebAssembly binary or boot Linux. Therefore:
* `bootVerified` remains `false`.
* `executionReady` remains `false`.
* Actual execution qualification and Linux boot verification must be tested in the browser runtime.
